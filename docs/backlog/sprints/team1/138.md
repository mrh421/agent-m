### The probe build — this sprint's procedure

1. The Developer makes a probe build of its item in its worktree: code only, not pushed, not committed to the item's
   branch.
2. It runs, file by file (no full local run), skipping the six files that hang locally and giving each file at most 60
   seconds: the test files of the item's modules, of the modules that import them, of the modules whose generated files
   the change feeds (for ITM-700: `docs/index.html`, `index.html`), and every test that reads a changed file by its path.
   It renders each route it changes with every context the dashboard hands it: the instance and a product, on the main
   page and on the review page. It reports to the Scrum Master every existing expectation that moves (file:line, test
   identifier, old → new), every real break, and, for ITM-700, the time of `tests/site-frame-preloads.test.mjs` alone.
3. The Product Owner edits the open item's Acceptance to name each moved expectation the accepted text allows to change,
   and any fixture or generated-file change. One the text does not allow is a finding, named here; if the item cannot be
   built so, it leaves the selection with its reason, for akmaier.
4. Only then the job proper: the tests-only commit, with the named changed expectations (red on CI, unless the item is
   declared refactoring); then the code.

### The brief — the team agreements, stated here

Reading and reporting
- Open each report with one line listing every document you read in full and its number of lines, this record among
  them; the Scrum Master checks it.
- For every module whose values the change touches, read its interface types, not only its prose. Call only what the
  caller's Uses and the callee's interface give; import nothing the Uses do not name.
- Read every search to its last line, for each count and expectation the change touches, and confirm a negative on a
  case that must match.

Scope
- Change nothing but the item's modules and the tests its Acceptance names; before anything else, stop and ask the
  Product Owner.
- YAGNI: build the accepted text and the Acceptance and nothing beyond. Any reading the texts leave open is named in the
  pull request, or you stop under AGENTS.md §6a.6 naming the missing sentence. No SPEC changes in this sprint.
- When what a view derives changes, check it on each page that draws the changed field, with each value the field can
  take.
- A value added to a list or family takes the shape of those already in it. Before renaming, search `docs/` and `src/`
  for every reader.
- No top-level await in any module. Run the tests of the modules that import the one you change. CI runs Node 22.

Tests
- The probe comes before the first commit and is never pushed. It skips the six locally hanging files, gives each file
  at most 60 seconds, and reports what it has.
- A probe also runs the tests of the modules whose generated files the change feeds, and renders each changed route in
  every context the dashboard hands it.
- The first commit holds only tests, and CI is red on it for the item's reason, unless the item is declared refactoring.
  Changed expectations are in that commit; no counter-proof is weakened later. Run
  `tests/test-document-one-line.test.mjs` before pushing it.
- A test file's `Module:` header names one module per line. A new test names the requirement or use case it guards by
  its identifier, never by a step. Every known positive or counter-proof it names is asserted in its own case.
- Before using a new test identifier, search the history for it (`git log --all -E -G <pattern> -- tests docs src`).
- A removed test names what it guarded and the test that guards it now.
- A release test's finding is a FINDING `todo`, ruled at the gate: registered, a new item, or for akmaier. A finding in
  another module's code names that module's item.

Pushing and CI
- Open the pull request as soon as the tests-only commit is pushed; push and report without waiting for CI. The Scrum
  Master watches the runs; nobody waits on CI for more than 2 minutes.
- A rework that rebuilds the branch pushes the tests-only commit first, and the code only after that run has started.
- A pull request's description names its own job only. A merge commit that resolves a conflict carries its author's
  trailers.
- A commit an Acceptance gives another participant that describes the item's code is written only after that code is
  pushed, from the pushed code. The Scrum Master asks for it then, and names the item to the Product Owner only once that
  commit is on the branch.
- Gate records give `on:` as a list.
- At each gate, the reads and calls of a changed function are counted against the base, on unchanged paths too.
- Run only the test files the change needs, one at a time; no full local run.
