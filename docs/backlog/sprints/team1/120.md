## ITM-1267's stop: decided (po-opus-c)

**ITM-1267 leaves the sprint and waits for a draft for akmaier.** developer-opus-e's patch is kept as it stands
(`scratchpad/ITM-1267.patch`, 45 files). Nothing of it is committed, and its branch is not merged.

- **What stopped it.**
  - The patch's run took 388 files. It fails 223 of them, against 19 without the patch, all of those machine-bound. So
    204 files and 1,425 cases fail only with the patch, 29 of the files release tests.
  - Most call `render` on a route of a view's `routes` (`view.routes.find(…).render`). With the patch, that route is a
    stand-in of `name`, `entry`, `title` and `module`, with no `render`.
- **The texts decide that this is an interface, not a test convention.**
  - MOD-site-frame gives `View` as `{ routes: Route[], … }` (MOD-site-frame.md:153).
  - It gives `Route` with `render(target, context, params) -> Promise<void>` as a member every route has. `subject`,
    `leave`, `unsaved`, `reads`, `folders` and `module` are marked optional with `?` (:156-162); `render` is not.
  - So a test that renders a route of `view.routes` uses the interface as accepted. A stand-in without `render` breaks the
    accepted `Route`, whatever :181-185 says of what "stands in the view module". Changing 204 test files to fit that
    would make the code the judge of the interface (AGENTS.md §6a.7).
- **Why no reading of the texts lets the item go on.**
  - The two sentences can both hold only if a stand-in still carries `render`, and a `subject` where its route has one,
    each importing the route's file before it calls the real one.
  - Each of the six views would then hold that same delegation, which is a rule kept in six copies (AGENTS.md §2,
    principle 2; DON'T REPEAT YOURSELF).
  - Held once, it is a function of MOD-site-frame that the views call. MOD-site-frame's `provides` holds no such function,
    and no view's Uses names one.
  - The synchronous `leave() -> boolean` and `unsaved() -> boolean` cannot wait for an import. Their answer for a route not
    yet loaded is in no text.
  - So no implementation is possible without a change of the architecture, which is akmaier's (AGENTS.md §2, §6a.6).
- **The draft for akmaier, at MOD-site-frame, with the six views' Uses.**
  - MOD-site-frame provides the one way a view writes a stand-in: from a route's head and its `module`, it gives a
    `Route`. Its `render`, and its `subject` where its route has one, import the route's file once and call it.
  - It states what `leave` and `unsaved` answer for a route not yet loaded: `true` and `false`, since nothing is shown.
  - Each view's Uses name that function.
  - `View.routes` stay whole `Route`s, so the tests that render a view's route keep their meaning. Only tests that check a
    stand-in's own members, patch them, or read `dashboard-app.mjs` as text then change.
- **For the draft and the item: the two-minute budget.** `tests/site-frame-preloads.test.mjs` took 44 s with the patch
  under parallel load, and 28 s alone, against 2.5 s before. The patch evaluates every view module in a child Node.
  A PULL REQUEST'S CI RUNS WITHIN TWO MINUTES (SPEC.md:1559-1563), so the item names the time of its CI job before it is
  selected again.
- **The patch's two readings, for the draft:**
  - "`module` gives the route" means `module` resolves to the route's file, and the head stands over it. That is right by
    :162 and :183.
  - The data of the route modules is keyed by route name. That is right, since `name` is the route's identifier in the
    address (:166).
- **Measured, kept for the next selection.** `#uc` loads 230 modules and 787 KB gzipped, against the item's expected
  ~214 and ~707 KB. Service modules that the strategies import make the difference, and `#uc` no longer loads
  maintenance, settings or mail.
- **For the retrospective:**
  - The planning check of the Uses read MOD-site-frame's prose on stand-ins (:181-185), not the `Route` type above it.
  - Reading the type would have shown, before selection, that a stand-in in `View.routes` must still render.
