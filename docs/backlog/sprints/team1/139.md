### The brief — the team agreements, stated here

Reading and reporting
- Your report opens with one line naming each document you read in full, with its line count; this record is one of
  them. The Scrum Master checks that line.
- For each module whose values your change touches, read its interface types as well as its prose. Call only what your
  module's Uses and the callee's interface give; import nothing the Uses leave out.
- Read each search to its last line for every count and expectation the change touches, and confirm a negative against a
  case that has to match.

Scope
- Change only the item's module and the tests its Acceptance names; for anything else, stop and ask the Product Owner
  first.
- YAGNI: build what the accepted text and the Acceptance say, nothing more. A reading the texts leave open goes into the
  pull request, or you stop under AGENTS.md §6a.6, naming the sentence that is missing. Nobody changes the SPEC this
  sprint.
- If what a view derives changes, check every page that draws the changed field, with each value it can take.
- A new member of a list or family takes the form its siblings have. Before a rename, search `docs/` and `src/` for all
  readers.
- No module awaits at its top level. Run the tests of the modules that import the one you change. CI uses Node 22.

Tests
- The probe build comes before your first commit and is never pushed. It leaves out the six files that hang locally,
  allows each file 60 seconds at most, and reports what it found.
- The probe also runs the tests of the modules whose generated files the change feeds, and renders every changed route in
  each context the dashboard gives it.
- A probe that finds a real break outside the item's modules reports it straight away, before it runs the remaining
  files.
- The first commit holds tests only, and CI is red on it for the item's reason. Every changed expectation is in that
  commit; no counter-proof is weakened afterwards. Run `tests/test-document-one-line.test.mjs` before pushing it.
- A test file's `Module:` header gives one module per line. A new test names the requirement or use case it guards by its
  identifier, never by a step. Each known positive or counter-proof it names has a case of its own that asserts it.
- Search the history for a new test identifier before using it (`git log --all -E -G <pattern> -- tests docs src`).
- A removed test names what it guarded and which test guards it now.
- A release test's finding is a FINDING `todo`, ruled at the gate: registered, made a new item, or sent to akmaier. A
  finding in another module's code names that module's item.

Pushing and CI
- Open the pull request once the tests-only commit is pushed; push and report without waiting on CI. The Scrum Master
  watches the runs; nobody waits on CI longer than 2 minutes.
- A rework that rebuilds the branch pushes the tests-only commit first, and the code only after that run has begun.
- A pull request's description speaks of its own job only. A merge commit that resolves a conflict carries its author's
  trailers.
- A commit that an Acceptance gives to another participant and that describes the item's code is written only after that
  code is pushed, and from the pushed code. The Scrum Master asks for it then, and names the item to the Product Owner
  only once that commit is on the branch.
- Gate records give `on:` as a list.
- At each gate, the reads and calls of a changed function are counted against the base, on unchanged paths as well.
- Run only the test files the change needs, one after another; never a full local run.
