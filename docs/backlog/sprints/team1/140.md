### The probe build — this sprint's procedure

1. The Developer makes a probe build of its item in its worktree: code only, not pushed and not committed.
2. It runs the tests of its module, of the modules that import it, and every test that names a function it changes. It
   runs them file by file, at most 60 seconds each, and skips the six files that hang locally. It renders each changed
   route in every context the dashboard gives it. If it finds a real break outside its module, it reports that to the
   Scrum Master at once, before the rest of the files run. Otherwise it reports every moved expectation (file:line, test
   identifier, old → new) and every real break.
3. The Product Owner edits the open item's Acceptance to name each moved expectation that the accepted text allows to
   change. One that the text does not allow is a finding, named here. An item that cannot be built so leaves the
   selection, for akmaier.
4. Then the job: the tests-only commit, red on CI; then the code. If the only moved expectation is a release test, the
   implementer writes its own red unit test. developer-sonnet-l then changes the release test and takes away its `todo`
   in one commit after the code.

### The brief — the team agreements, stated here

Reading and reporting
- Open your report with one line that names each document you read in full, with its line count. This record is one
  of them. The Scrum Master checks that line.
- For each module whose values your change touches, read its interface types as well as its prose. Call only what your
  module's Uses and the callee's interface give. Import nothing the Uses leave out.
- Read each search to its last line for every count and expectation the change touches. Confirm a negative against a
  case that has to match.

Scope
- Change only the item's module and the tests its Acceptance names. For anything else, stop and ask the Product Owner
  first.
- YAGNI: build what the accepted text and the Acceptance say, and nothing more. If the texts leave a reading open, put
  it in the pull request. Or stop under AGENTS.md §6a.6 and name the sentence that is missing. Nobody changes the SPEC
  this sprint.
- If what a view derives changes, check every page that draws the changed field, with each value it can take.
- A new member of a list or family takes the form of its siblings. Before a rename, search `docs/` and `src/` for all
  readers.
- No module awaits at its top level. Run the tests of the modules that import the one you change. CI uses Node 22.

Tests
- The probe build comes before your first commit and is never pushed. It skips the six files that hang locally, gives
  each file 60 seconds at most, and reports what it found.
- The probe also runs the tests of the modules whose generated files the change feeds. It renders every changed route
  in each context the dashboard gives it.
- If a probe finds a real break outside the item's modules, it reports it at once, before it runs the remaining files.
- The first commit holds tests only, and CI is red on it for the item's reason. Every changed expectation is in that
  commit. No counter-proof is weakened afterwards. Run `tests/test-document-one-line.test.mjs` before you push it.
- If an item's only moved expectation is a release test, the implementer writes its own red unit test. The release
  test's change and its `todo` go in one commit by another participant, after the code.
- A test file's `Module:` header gives one module per line. A new test names the requirement or use case it guards by
  its identifier, never by a step. Each known positive or counter-proof it names has a case of its own that asserts it.
- Before you use a new test identifier, search the history for it (`git log --all -E -G <pattern> -- tests docs src`).
- A removed test names what it guarded and which test guards it now.
- A release test's finding is a FINDING `todo`. It is ruled on at the gate: registered, made a new item, or sent to
  akmaier. A finding in another module's code names that module's item.

Pushing and CI
- Open the pull request once the tests-only commit is pushed. Push and report without waiting on CI. The Scrum Master
  watches the runs, and nobody waits on CI for longer than 2 minutes.
- A rework that rebuilds the branch pushes the tests-only commit first. It pushes the code only after that run has
  begun.
- A pull request's description speaks of its own job only. A merge commit that resolves a conflict carries its author's
  trailers.
- A commit that an Acceptance gives to another participant, and that describes the item's code, is written only after
  that code is pushed, and from the pushed code. The Scrum Master asks for it then. It names the item to the Product
  Owner only once that commit is on the branch.
- Gate records give `on:` as a list.
- At each gate, the reads and calls of a changed function are counted against the base, on unchanged paths as well.
- Run only the test files the change needs, one after another. Never do a full local run.
