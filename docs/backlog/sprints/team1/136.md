### The probe build — this sprint's procedure, for each item

1. The Developer makes a probe build of the item in its worktree: code only, not pushed, not committed to the item's
   branch.
2. It runs the test files of the item's modules and of the modules that import them, file by file (no full local run),
   skipping the six files that hang locally (below) and giving each file at most 60 seconds; it reports to the Scrum
   Master what it has: every existing expectation that moves (file:line, test identifier, old → new) and every real
   break.
3. The Product Owner edits the open item's Acceptance to name each moved expectation that the accepted text allows to
   change, and any fixture change. An expectation the text does not allow to change is a finding, named in this record;
   an item that cannot be built so leaves the selection with its reason, for akmaier.
4. Only then the job proper: the tests-only commit(s), with the named changed expectations, red on CI; then the code.
   The probe itself is never pushed.

### The brief, for every item — the team agreements, stated here

Reading and reporting
- The first line of a report lists the documents read in full, with their line counts, this record among them; the
  Scrum Master checks it.
- Read the interface types of every module whose values the change touches, not only the prose. Use only what the
  calling module's Uses and the called module's interface state; import nothing its Uses do not name.
- A search is read to its end and looks for every count or expectation the change touches. A negative is checked
  against a known positive.

Scope
- Change only the item's modules and the tests its Acceptance names; stop and ask the Product Owner before any other.
- YAGNI: build only the accepted text and the Acceptance. A reading the texts leave open is named in the pull request, or
  the item stops under AGENTS.md §6a.6 with the missing sentence. No item of this sprint changes the SPEC.
- An item that changes what a view derives checks every page that draws the changed field, with each value it can take.
- A value added to a list or family takes the shape of the existing ones. A rename first searches `docs/` and `src/` for
  every reader.
- No top-level await in a module; run the tests of the modules that import the changed one. CI runs Node 22.

Tests
- This sprint's probe build comes before the first commit, as above; it is not pushed. A probe skips the six files that hang
  locally (below), gives each file at most 60 seconds, and reports what it has.
- The first commit holds only the tests, and CI is red on it for the item's reason. A changed expectation stands in that
  commit, and no counter-proof is weakened later. Run `tests/test-document-one-line.test.mjs` before pushing it.
- A test file's `Module:` header names one module per line. A new test names the requirement or use case it guards by
  its identifier, never by a step. Every known positive or counter-proof it names is asserted in its case.
- A new test identifier is searched for in the history first (`git log --all -E -G <pattern> -- tests docs src`).
- A test removed names each thing it guards and the test that keeps guarding it.
- A release test's finding is written as a FINDING `todo`, and ruled at the gate: registered, a new item, or for akmaier.
  A finding pointing into another module's code names that module's item.

Pushing and CI
- Open the pull request right after pushing the tests-only commit; push and report without waiting for CI. The Scrum
  Master watches the runs. Nobody waits on CI more than 2 minutes.
- A rework that rebuilds a branch pushes the tests-only commit first, and the code only after its run has started.
- A pull request's description names only its own job. A merge commit that resolves a conflict carries its author's
  trailers.
- When an Acceptance gives a commit to another participant, the Scrum Master asks for it once the code is pushed, and
  names the item to the Product Owner only once it is on the branch.
- Gate records write `on:` as a list.
- At each gate, the reads and calls of a changed function are counted against the base, also on unchanged paths.
- Run only the test files the change needs, one by one; no full local run.
